## A. Umsetzen

### 1. Alarm wirft → Absturz bei jedem Start — Risiko, für HOME ein Boot-Loop
- `Guru.kt:97-105` `present` läuft ungeschützt auf Main: Host-Texte (`texts.saved(count)`,
  `hint`, … — `getString` auf eine nach der 2.0-Migration fehlende Ressource), Bau von
  `GuruView`, `Dialog.show()`, Layout und `onDraw`.
- Wirft dort etwas deterministisch, schreibt der Handler einen Bericht, der nächste Start
  sichert ihn und zeigt den Alarm — der wieder wirft. Jeder Start: eine Datei mehr, ein Absturz
  mehr. Die alte Schleife (Bericht blieb offen) ist weg, diese nicht.
- **Nachgeprüft:** ja, im Code; von zwei Agents unabhängig gefunden.
- **Vorschlag:** (a) `present` in `try/catch (RuntimeException)` — deckt den synchronen Teil;
  (b) für Layout/Draw: den Alarm auslassen, wenn der neueste gesicherte Bericht ein CRASH auf
  `main` ist, dessen oberste Frames in `com.github.reygnn.guru` liegen. Die Datei ist gesichert;
  nur der Hinweis entfällt. README/CHANGELOG-Satz entsprechend ehrlich formulieren.

### 2. Dedup Crash ↔ Exit-Eintrag nur noch innerhalb eines Starts — wahrscheinlicher Bug
- `Guru.kt:164` nimmt `handlerTimes` aus `store.pending()`. Früher blieb ein Handler-Bericht
  liegen, bis der Nutzer handelte; jetzt wird er im Start direkt nach dem Absturz gesichert und
  gelöscht.
- Steht der Exit-Eintrag in diesem Start noch nicht in `getHistoricalProcessExitReasons`
  (AMS trägt ihn asynchron ein; ein Launcher startet in Millisekunden neu), wird er beim
  übernächsten Start „neu“ — ohne Handler-Zeit daneben → zweiter CRASH-Bericht ohne Trace, neue
  `REPORT_ID`, das Backend zählt doppelt. **Wie spät der Eintrag kommen kann: nicht geprüft.**
- **Vorschlag:** die `crashedAt` gesicherter CRASH-Berichte in einer kleinen Datei im Store
  aufheben (letzte 8 oder 1 h) und in `handlerTimes` mitgeben.

### 3. „Einmal“ wird verbraucht, bevor der Alarm erscheint — Risiko (UX)
- `Guru.kt:88-93` leert `s.saved` auf io; `present` kann danach aussteigen (Activity neu
  erzeugt: Dunkelmodus nach Zeitplan, Wallpaper/dynamische Farben, Schrift, Sprache), und
  `DismissOnDestroy` schließt einen schon sichtbaren Alarm bei jeder Neuerzeugung. Die neue
  Activity zeigt nichts. Keine Daten weg — nur der einzige Hinweis.
- **Vorschlag:** steigt `present` aus, die Liste zurückgeben (`s.io { s.saved = saved + s.saved }`);
  schließt `DismissOnDestroy` wegen `isChangingConfigurations`, ebenso. Läuft nur im Speicher
  eines Prozesses, kann also nicht schleifen.

### 4. CI baut den Gerätetest nicht — Risiko
- `./gradlew check` enthält `lintAnalyzeDebugAndroidTest`, aber nicht
  `compileDebugAndroidTestKotlin`. Bricht ein Update den androidTest (auch eine Warnung unter
  `allWarningsAsErrors`), bleibt CI grün bis zum Gerätetest vor dem Tag.
- **Vorschlag:** `check` hängt von `:library:compileDebugAndroidTestKotlin` ab.

### 5. Gerätetest-Schritte 2–4 sind nicht durchführbar — Doku/Bug im Verfahren
- Schritt 2: Halten schließt den Alarm, danach gibt es nichts mehr doppelzutippen.
- Schritt 3: „Crash twice, start: 2 reports saved“ — jeder Start sichert sofort; zwei offene
  Berichte bekommt man von Hand nicht hin. Und guru2acra nimmt `application/json` noch nicht an.
- Schritt 4: „vor dem Alarm noch einmal abstürzen“ geht von Hand nicht (Millisekunden).
- Schritt 1: `am crash` braucht einen laufenden Prozess.
- **Vorschlag:** im Sample (nur Debug) einen Knopf „Absturz vor dem Sichern“: setzt ein Flag,
  stürzt ab; der nächste Start stürzt in `onCreate` ab, bevor `io` sichert → zwei offene
  Berichte. Schritte neu schreiben; guru2acra-Schritt erst, wenn guru2acra so weit ist.

### 6. Testlücken (Mutanten überlebt) — je ein Test
1. **G10** `showPending` ohne `isNotEmpty`: `present` würfe auf Main bei jedem Start ohne
   Sicherung — die Tests merken es nicht, weil `onUi { it() }` synchron im Guard läuft. Test mit
   aufgeschobenem `onUi`: nichts eingereiht.

3. **D04** Nicht-ASCII-Trace (`Grüße ✓ 版 😀`) kommt byte-genau zurück.

   falsche Selection ablehnen.
5. **G27** versionName des Hosts erscheint im Dateinamen (ShadowPackageManager).
6. **D12** `KEEP == 32` festnageln.
7. **G06** beschlossen: geprunt wird, sobald Berichte offen waren — Test „alle Sicherungen
   abgelehnt, 33 eigene Dateien“ oder den Testnamen „nothing saved prunes nothing“ korrigieren.
8. **S06** `performLongClick()` liefert true; **D07** null-Descriptor im Fake (klein).

## B. Abwägen

### 8. Haltbarkeit über einen Stromausfall — Risiko, nicht geprüft
- Daten werden gesynct, aber MediaProviders Umbenennung `.pending-…` → Name und sein SQLite-WAL
  sind es vielleicht nicht; Gurus `delete()` auch nicht. Auf f2fs kann das Löschen überleben,
  die Zeile aber auf `IS_PENDING=1` zurückfallen → nach ~7 Tagen von MediaStore entfernt.
- **Vorschlag:** Gurus Kopie erst beim *nächsten* Start löschen, nachdem die Zeile mit
  `IS_PENDING=0` bestätigt ist — oder einen Satz in die README.

### 9. Die vierte Zeile bestimmt die Schriftgröße des ganzen Alarms — klein — **erledigt in 2.0.1**
- `fit` passt alle Zeilen an die breiteste an; „8 Berichte in Download/Guru gespeichert“ (39)
  ist länger als die Amiga-Zeile (36) → Alarm auf 360 dp von ~13,7 auf ~12,6 sp. Host-Zeile
  getrennt einpassen oder Hosts ≤ 36 Zeichen empfehlen.

### 10. Weiteres
- Mehrprozess-Hosts sichern doppelt (gleiche `REPORT_ID`) → „install nur im Hauptprozess“ dokumentieren.
- `label(app)` ungeschützt auf Main in `install` (wirft praktisch nie) — wie `environment()` fangen.
- `RELATIVE_PATH =` ist case-sensitiv; existiert schon `Download/guru`, prunt Guru nichts.
- `actionShare` „share the report“ bei mehreren Dateien.
- Kontrast des Hinweises (0x666666 ≈ 3,7 : 1, Audit-23 #12) weiter offen.
- Löschen ist für den Nutzer nicht auffindbar (nur README).
- Dateiname: Kombinationszeichen → `_`, führender `.` → versteckte Datei (Audit-24 C.11).
